# Plan : Migration NutriAnalyse Pro v2 vers golem

**Date** : 27 mars 2026  
**Projet** : NutriAnalyse Pro v2 → paquet R structuré avec `{golem}`

---

## Pourquoi golem ?

L'architecture actuelle fonctionne, mais présente des limites d'ingénierie importantes :

| Problème actuel | Ce que golem apporte |
|---|---|
| 49 `source()` dans un fichier de 8 739 lignes | Package R chargé automatiquement, plus aucun `source()` |
| 39 `library()` dans l'app | `DESCRIPTION (Imports:)` — dépendances déclaratives, vérifiées au build |
| Démarrage : `shiny::runApp("app_v2_final.R")` | `NutriAnalysePro::run_app()` — lançable depuis n'importe où |
| Déploiement manuel sur Connect / shinyapps.io | `golem::add_dockerfile()` + `rsconnect::deployApp()` automatisé |
| Tests sans contexte package | `testthat` + `shinytest2` + `golem::check_selected_tests()` |
| Configuration hardcodée (clés API, seuils OMS) | `golem::get_golem_options()` + `golem-config.yml` |
| Impossible d'installer l'app comme un package | `remotes::install_github("yimgakevin/NutriAnalysePro")` |

## Plan de migration en 6 phases

### Phase 1 — Initialisation golem (~15 min)

Installer golem puis créer le squelette dans le répertoire courant :

```r
install.packages("golem")

golem::create_golem(
  path         = "C:/Users/Yimga kevin/Documents/Shiny_entreprise",
  package_name = "NutriAnalysePro",
  open         = FALSE
)
```

Cela génère automatiquement :
- `DESCRIPTION`, `NAMESPACE`
- `R/app_ui.R`, `R/app_server.R`, `R/app_config.R`, `R/run_app.R`
- `dev/01_start.R`, `dev/02_dev.R`, `dev/03_deploy.R`
- `inst/app/www/`, `golem-config.yml`

> ⚠️ Avant d'exécuter : le backup `app_v2_final.R.backup` existe déjà, c'est suffisant.

### Phase 3 — Migration des fichiers R (~30 min)

**3a. Créer le dossier `R/`** et déplacer les 69 fichiers `.R` depuis la racine vers `R/`.

**3b. Diviser `app_v2_final.R`** en deux fichiers golem :

`R/app_ui.R` :
```r
app_ui <- function(request) {
  tagList(
    golem_add_external_resources(),
    dashboardPage(
      header  = ...,   # contenu actuel du header
      sidebar = ...,   # contenu actuel de la sidebar
      body    = ...    # contenu actuel du body
    )
  )
}
```

`R/app_server.R` :
```r
app_server <- function(input, output, session) {
  # Tout le contenu du server actuel
  # SANS les source() — fonctions disponibles via package
}
```

**3c. Supprimer tous les `source()` et `library()`** :
- Les `library()` → `DESCRIPTION Imports:` (déjà fait en Phase 2)
- Les `source()` → supprimés, le chargement du package suffit

**3d. Gérer les `source(..., local=TRUE)`** (utilisés dans le server pour carto) :
Ces blocs appellent des fichiers qui injectent du code dans le scope server. Il faut les transformer en fonctions exportées appelées depuis `app_server.R`. Exemple :
```r
# Avant
source("carto_server_outputs.R", local = TRUE)

# Après (dans app_server.R)
carto_server_outputs(input, output, session, ...)
```

**3e. Mettre à jour `R/run_app.R`** :
```r
#' @export
run_app <- function(...) {
  with_golem_options(
    app      = shinyApp(ui = app_ui, server = app_server),
    golem_opts = list(...)
  )
}
```

## Points d'attention / risques

1. **`source(..., local=TRUE)`** dans le server (fichiers carto) → transformer en fonctions (`carto_server_outputs`, etc.) — c'est le seul vrai travail de refactoring.
2. **Variables globales** (`TRANSLATIONS`, `GADM_WORLDWIDE`, `OMS_SEUILS`) — elles restent en tant qu'objets chargés au niveau package, pas de changement nécessaire.
3. **Cache GADM** (`gadm_cache/`) — reste dans la racine du projet, référencé via `here::here("gadm_cache")` ou `golem::get_golem_options("gadm_cache_dir")`.
4. **`golem::create_golem()`** — ne va pas écraser les fichiers existants s'ils existent déjà ; il crée uniquement les fichiers manquants.
5. **Tests** — les `source()` dans les fichiers de test devront être remplacés par `library(NutriAnalysePro)` ou `devtools::load_all()`.
